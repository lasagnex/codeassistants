### T004 – Vehicle Sensor EDA and Braking Measurement Analysis (Medium)

**Difficulty:** Medium
**Category:** Data analysis, EDA, signal processing, reporting

## Task Description
During a test session, front axle brake and wheel sensors of a truck were recorded and exported to
`t004_vehicle_data.xlsx` (sheet `000`, ~1.05 million rows, sampled at 100 ms; there is no time
column — derive the time axis from the sampling rate and the row order).

Build an analysis tool that first repairs the inconsistencies in this recording and then turns the
cleaned data into an engineering report: a general exploratory data analysis (EDA) plus detection
and characterisation of the individual braking events.

Dataset columns:

| Column   | Unit | Description                                          |
|----------|------|------------------------------------------------------|
| `t_amb`  | °C   | ambient air temperature                              |
| `p_a1l`  | bar  | brake pressure, front left wheel                     |
| `p_a1r`  | bar  | brake pressure, front right wheel                    |
| `v_a1l`  | km/h | wheel speed, front left wheel                        |
| `v_a1r`  | km/h | wheel speed, front right wheel                       |
| `t_a1l`  | °C   | brake disc temperature, front left wheel             |
| `sys_ok` | 0/1  | system health flag; `0` marks a degraded acquisition |

The raw data is not clean. It contains at least missing values, non-numeric entries, sentinel
values used instead of a reading, sensor dropouts and physically implausible samples. Finding and
justifying these is part of the task — do not assume the list above is complete, and do not invent
issues that are not in the data.

## Requirements
- **Data quality & repair:** detect and repair the inconsistencies (missing/duplicated samples,
  non-numeric entries, out-of-range values, sentinel readings, dropouts).
  Keep a repair log listing every detected issue, the exact remediation applied and why.
  Repairs must preserve physical plausibility (speed cannot be negative, pressure and temperature
  limits must be justified). All removed data must be quantified and justified.
- **Dataset overview:** time span, sampling rate, sensors, per-signal basic statistics, coverage
  of the `sys_ok` flag.
- **Exploratory analysis:** distributions, time plots, correlations and the relationships that
  matter physically (pressure vs. deceleration, pressure vs. disc temperature, left/right balance,
  disc temperature vs. ambient temperature).
- Detect braking events: a contiguous window where brake pressure is above a justified threshold
  and wheel speed is decreasing. Merge events separated by less than 0.5 s, discard events shorter
  than 0.3 s.
- Per event, report:
  - start/end time, duration, entry and exit speed,
  - mean and peak deceleration derived from the wheel speeds,
  - stopping distance (integrated speed),
  - peak pressure left/right and the left/right pressure ratio (brake force balance),
  - left/right wheel speed difference and the maximum relative slip between the two front wheels,
    `slip = (v_ref - v_wheel) / v_ref` with a documented reference speed, clamped to `[0, 1]`,
  - disc temperature rise over the event,
  - a pass/fail flag: FAIL if the peak deceleration magnitude stays below `4.0 m/s²` while pressure
    was above 80 % of its observed maximum (high pressure that does not produce braking effect).
- Dropouts and `sys_ok = 0` stretches must not produce NaN results or false events; how you handled
  them (interpolation, gap rejection, ...) and why must be documented.
- Filter noisy signals before deriving deceleration; justify the filter choice and cutoff.
- All findings must be grounded in the dataset; do not invent values or events.
- Plots must be readable and labelled (axes, units, legends); time-series plots use time on the
  x-axis.
- The tool takes the input file path as an argument; nothing may be hardcoded to a fixed path.
  Reading the full file must not require loading it repeatedly.

## Expected Deliverables
- **The EDA report** (Markdown, HTML or PDF) — the main deliverable — containing:
  - dataset overview: time span, sampling rate, sensors and basic statistics,
  - data quality & repair log: every detected issue and the exact remediation applied,
  - exploratory analysis: distributions, time plots, correlations and relationships,
  - the braking event analysis with the per-event table and the per-event plots,
  - key takeaways: 5–10 bullet insights, every one grounded in the data.
- A machine readable summary of the results (JSON or CSV).
- The source code of the analysis tool.
- The test suite and the small data fixture it runs on.
- A README with setup, run instructions, runtime, and a short interpretation of the results.

## Testing
- Unit tests for the cleaning rules: non-numeric entry, sentinel value, out-of-range sample,
  missing sample, duplicated sample — each must be detected and repaired as documented.
- Unit tests for event detection using synthetic signals with a *known* number of events,
  including the merge and minimum-duration rules.
- Unit tests for slip calculation, including `v_ref = 0` (division by zero) and wheel overspeed.
- A test proving the stopping distance calculation against an analytically known constant
  deceleration case, within a stated tolerance.
- A regression test running the full pipeline on a small fixture extracted from the provided
  dataset (commit the fixture, not the full workbook).
