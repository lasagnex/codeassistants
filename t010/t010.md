### T010 – Add an `xdd` / `.xdc` Database Format to `canmatrix` (Hard)

**Difficulty:** Hard
**Category:** Large open-source repo integration, plugin architecture, data-model round-trip

## Context
**canmatrix** is an open-source Python library that reads and writes CAN bus database descriptions
(DBC, ARXML, KCD, SYM, DBF, XLS/XLSX, JSON, YAML, CSV, …) around a common in-memory model
(`CanMatrix`, `Frame`, `Signal`, `Ecu`, value tables, defines/attributes, multiplexing). We want to
add a new first-class format, **XDD** (XML-based device description, files `.xdd` / `.xdc`), to that
list.

- Repository: `https://github.com/ebroecker/canmatrix`
- Pinned checkout: commit **`8db6b9f9b143c86dc82cfe085485afeecee160d4`**. Check this exact commit out
  before making any changes.

## Task Description
Add a new first-class database format module **`xdd`** (`.xdd` / `.xdc`) to canmatrix.

- Implement `canmatrix/formats/xdd.py` containing both `load(file, **options)` and
  `dump(db, file, **options)`.
- Register `.xdd` and `.xdc` in `canmatrix/formats/__init__.py` so auto-selection works seamlessly
  with `canmatrix.formats.load()` and `canmatrix.formats.dump()`.
- Update the command-line tool discovery so `canconvert input.dbc output.xdd` works without any
  additional flags.
- Add unit tests covering **round-trip conversions** (`dbc -> xdd -> dbc`) in the repository's exact
  test directory — **verify whether this checkout uses `src/canmatrix/tests/` or `tests/`** and put
  them there.

`.xdd` is the human-readable description and `.xdc` is a configured variant of the same schema; both
extensions map to the same module. The serialization must be a **lossless, well-formed XML**
representation of the canmatrix model. The headline acceptance test is a **round-trip**: converting
one of the repository's own sample databases to `.xdd` and back must reproduce a semantically
identical `CanMatrix`, verified with canmatrix's **own comparison facility** (`compare` /
`cancompare`), with **zero differences** — except for fields you explicitly document as intentionally
out of scope, each with a justification.

### XML schema strategy
Implement a **canonical XML schema that maps 1:1 to canmatrix's internal objects** (`CanMatrix`,
`Frame`, `Signal`, `Ecu`, value tables, defines/attributes, multiplexing). Do **not** implement a
full ISO 15745 / CiA 311 Object Dictionary mapping — the goal is a clean,
lossless XML representation of the canmatrix model so that `DBC -> XDD -> DBC` round-trips with
**zero** comparison differences. Model the XML element/attribute names directly after the canmatrix
fields; do not invent a semantic device-description layer.

## Requirements
- **Plugin integration, done the canmatrix way.** Register the new format through the same mechanism
  the existing formats use (loader/dumper discovery, extension mapping, `supportedFormats` or its
  equivalent). No monkey-patching, no bypassing the registry, no callers special-casing `xdd`.
  Adding the module plus the registration must be enough for both the API and the CLI to pick it up
  by extension.
- **Dump (model → XDD).** Serialize the full model, not just the easy fields:
  - all `Frame` attributes: id / arbitration id (standard **and** extended), DLC, transmitters,
    frame comment, cycle time, CAN-FD flag(s), and frame-level attributes/defines;
  - all `Signal` attributes: start bit, length, **byte order (Motorola/Intel)**, signedness,
    factor, offset, min, max, unit, initial value, receivers, signal comment, value tables / named
    values (enumerations), and signal-level attributes/defines;
  - **multiplexing**, including the multiplexer switch signal, multiplexed signals with their
    multiplex values, and **extended / complex multiplexing** where present;
  - `Ecu` list with comments/attributes, plus matrix-level defines, attribute defaults, value tables
    and environment/global metadata.
- **Load (XDD → model).** Reconstruct an equivalent `CanMatrix` from the XML produced by the dumper.
  Loading must be tolerant of hand-edits (missing optional elements fall back to model defaults) and
  must raise clear, actionable errors on malformed input — never a bare traceback from deep inside
  the XML parser.
- **Byte-order correctness.** Handle both bit-numbering conventions correctly so that Motorola
  (big-endian) and Intel (little-endian) signals survive the round-trip with identical bit
  placement. This is the classic trap in this codebase — get it right and prove it.
- **Compatibility.** Use the XML tooling already available to the project (e.g. `lxml` if it is
  already a dependency, otherwise the standard library) and declare any new dependency in the
  packaging metadata. Match the Python versions the project already claims to support. Keep the
  existing public API and all current tests passing.
- **Code quality.** Match the surrounding code's style and typing conventions. No new warnings; the
  project's existing lint / type-check configuration must stay clean.

## Expected Deliverables
