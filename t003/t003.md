### T003 – Debug the Wheel Speed Filter (Easy)

**Difficulty:** Easy
**Category:** Debugging, embedded C

## Task Description
The code below is a moving average filter used to smooth the wheel speed signal before it is fed
into the brake slip calculation. It is reported to produce wrong values: the very first outputs
after start-up are far too low, and once the filter has been running for a few cycles the output
jumps around wildly for no reason.

Your job is to find the defects, fix them, and prove the fix with tests.
Do **not** rewrite the module from scratch — keep the ring buffer approach and the API.

> **Starting code:** `base/` contains `wheel_speed_filter.c` and `wheel_speed_filter.h`

## Requirements
- Reproduce both reported symptoms before fixing anything — the root cause, not just
  "it was broken".
- Fix all defects you find. There is more than one.
- Keep the public API (`wsf_init`, `wsf_update`) unchanged.
- The filter must behave sensibly during the warm-up phase, i.e. before `WSF_WINDOW` samples
  have been collected the average must be taken over the samples actually received.
- No dynamic memory, no floating point, no C library calls beyond `<stdint.h>` — this runs on an ECU.
- The module must be safe to re-initialize at any time.

## Expected Deliverables
- The fixed `wheel_speed_filter.c` / `wheel_speed_filter.h`, with the public API unchanged.
- The unit test suite plus the build/run instructions for it.
- A README containing the root cause analysis: for each reported symptom, what actually happens in
  the original code and which defect causes it.

## Testing
- Unit tests (any C test framework, e.g. Unity, CMocka, or plain asserts in a main) covering:
  - constant input → output equals that input,
  - warm-up behaviour after `wsf_init`,
  - a step response (0 → 1500 rpm) sampled over more than 2 windows,
  - the maximum input value 3000 rpm held for many updates (no overflow, no wrap-around),
  - re-initialization mid-stream.
