### T009 – Port a Brake Diagnostics Module from C to Rust (Hard)

**Difficulty:** Hard
**Category:** Language port, bit-exact parity, FFI, protocol implementation

## Task Description
The team wants to evaluate Rust for future ECU software. The pilot is the **UDS (ISO 14229)
diagnostic session handler** of the trailer brake ECU, currently written in C. Port it to Rust and
prove that the port behaves identically to the original, byte for byte.

> **Starting code:**: The C module is provided in `base/legacy_c/`

`base/legacy_c/BEHAVIOUR.md` pins down every point ISO 14229 leaves open (check order, the scope of
the suppress bit, the deterministic seed generator, the power-on data). **Read it before porting —
it, not your reading of the standard, is what the Rust side must match.**

### Module specification
A request/response handler over a byte-oriented transport. Input: a request buffer + length.
Output: a response buffer + length (or "no response"). Stateful across calls.

Supported services:

| SID    | Service                       | Notes                                                        |
|--------|-------------------------------|--------------------------------------------------------------|
| `0x10` | DiagnosticSessionControl      | sub-functions: `0x01` default, `0x03` extended                |
| `0x22` | ReadDataByIdentifier          | DIDs: `0xF190` VIN (17 bytes), `0xF187` part number, `0x2A01` brake pad wear (4 bytes, one per wheel), `0x2A02` reservoir pressure (2 bytes, 0.01 bar/bit) |
| `0x2E` | WriteDataByIdentifier         | only `0xF187`, only in extended session, only after security access |
| `0x27` | SecurityAccess                | seed/key, level `0x01`; key = `seed XOR 0x5A5A5A5A` rotated left by 3 |
| `0x14` | ClearDiagnosticInformation    | clears stored DTCs                                            |
| `0x19` | ReadDTCInformation            | sub-function `0x02` reportDTCByStatusMask                     |
| `0x3E` | TesterPresent                 | sub-function `0x00`, suppressPosRspMsgIndicationBit supported |

Required behaviour:
- Positive response = SID + `0x40`, followed by the service payload.
- Negative response = `0x7F`, SID, NRC. Implement at least: `0x11` serviceNotSupported,
  `0x12` subFunctionNotSupported, `0x13` incorrectMessageLengthOrInvalidFormat,
  `0x22` conditionsNotCorrect, `0x31` requestOutOfRange, `0x33` securityAccessDenied,
  `0x35` invalidKey, `0x36` exceedNumberOfAttempts, `0x7F` serviceNotSupportedInActiveSession.
- The `suppressPosRspMsgIndicationBit` (bit 7 of the sub-function) suppresses the positive response.
- S3 session timeout: the extended session falls back to default after 5 s without a TesterPresent;
  time is injected, never read from a system clock.
- Security access: 3 failed key attempts → `0x36` and a 10 s lockout; a successful unlock is lost
  on session change.
- All buffers bounds-checked; a truncated or oversized request yields `0x13`, never a crash.

## Requirements
- **Rust implementation** (`uds_rs/`): `#![no_std]`-compatible, `#![forbid(unsafe_code)]` in the
  core logic, no heap allocation, `&[u8]` in / `&mut [u8]` out with a length result.
  Model sessions, security state and NRCs with enums and a `Result`-based error type — the port
  must be idiomatic Rust, not transliterated C with indices everywhere.
- **Parity proof**, the core of the task:
  - a differential test harness that feeds the *same* request sequences to both implementations
    (via FFI from Rust to the C, or by driving both from a Python/Rust runner) and asserts
    byte-identical responses and identical resulting state;
  - a corpus of hand-written sequences covering every service, every NRC listed above, session
    timeout, the lockout, and the suppress bit;
  - **fuzzing / randomized differential testing** over random byte sequences (documented tool:
    `cargo-fuzz`, `proptest`, AFL, ...) with the found corpus committed. Any divergence found must
    be either fixed or documented as an intentional, justified deviation.
- Also expose the Rust module through a C ABI (`extern "C"`) so it could drop into the existing
  build, and show the C-side test suite passing against the Rust implementation.

## Expected Deliverables
- The Rust implementation in `uds_rs/`, plus its `extern "C"` wrapper and the C-side test suite
  passing against it.
- The differential test harness, the hand-written sequence corpus and the fuzz target, with the
  fuzzer-found corpus committed.
- A list of every divergence found, each either fixed or documented as an intentional, justified
  deviation.
- A README covering the C-to-Rust construct mapping, what the type system made impossible by
  construction, any behaviour that could not be preserved, and an honest assessment of whether the
  port is worth it.

## Testing
- Unit tests on both sides for each service and each NRC.
- The differential corpus test and the fuzz target described above, both runnable by one command.
- Timing tests for the S3 timeout and the security lockout using injected time.
- Rust build clean under `clippy -D warnings`; C build clean under `-Wall -Wextra -Werror`.
