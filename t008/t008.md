### T008 – Hunt an Intermittent Fault in Brake ECU Firmware (Hard)

**Difficulty:** Hard
**Category:** Debugging, concurrency, RTOS, embedded C

## Task Description
A brake ECU running FreeRTOS shows a rare field fault: roughly once per several hours of driving,
the brake pressure setpoint jumps for a single cycle to an implausible value, the plausibility
monitor trips and the system falls back to the pneumatic backup circuit. The failure is not
reproducible on the bench by driving alone.

The relevant firmware is reproduced below. It has **more than one defect**; at least one is a
race condition, at least one is a lifetime/aliasing problem, and at least one is a latent
arithmetic problem that only shows up at extreme signal values.

Your job: build a harness that reproduces the fault deterministically, identify every defect,
fix them, and prove the fixes.

> **Starting code:** `base/legacy/` contains `brake_task.c`, plus `ecu_hal.h` /
> `ecu_hal.c` — the ECU vendor's platform layer (`can_msg_t`, `pwm_set_duty`, `diag_log_async`,
> `diag_log_flush`).
>
> The FreeRTOS headers are **not** provided: standing up the RTOS (simulator port or a documented
> thread-based mock) is part of the task, so `brake_task.c` does not compile until you supply them.
>
> Treat the `ecu_hal.h` contract as fixed — in particular, `diag_log_async` stores the caller's
> *pointer* and the string is dereferenced later from the idle hook. You may reimplement the HAL for
> your harness, but weakening that contract hides a defect instead of fixing it.

## Requirements
- Build a **host-side reproduction harness**. Use the FreeRTOS POSIX/Windows simulator port, or a
  documented equivalent (e.g. a thread-based mock of the RTOS API) — the point is a deterministic,
  automated reproduction, not real hardware. Stress the interleavings so that the fault appears
  reliably (e.g. injected preemption points, seeded scheduling, ThreadSanitizer).
- Find and analyse every defect. At minimum you must cover:
  - the unsynchronized sharing of `g_frame` and `g_setpoint_mbar` between tasks of different priority,
  - the lifetime/aliasing bug around the asynchronous log buffer,
  - the arithmetic defects in `compute_setpoint` and in the wheel speed unpacking.
- Fix all of them. Constraints for the fixes:
  - no dynamic allocation,
  - the actuator task must never block on the control task (it is the hard real-time path);
    a lock-free or double-buffer/seqlock style solution is expected — justify your choice,
  - keep the task priorities and periods as they are; if you must change them, argue why,
  - state explicitly which variables are shared and what protects each one.

## Expected Deliverables
- The host-side reproduction harness, deterministic and automated.
- The provided original code kept unmodified in the repository (`legacy/`) so the tests can be
  pointed at it.
- The fixed firmware sources.
- A regression test per defect, failing on the original code and passing after the fix.
- A **written analysis** per defect: what is wrong, the triggering interleaving or input, the
  observable effect, and why it is rare in the field.
- A documented statement of which variables are shared and what protects each one, plus the
  residual risk your harness cannot detect.
- A README with the build and run instructions, including the reproduction seed / injection points.

## Testing
- Deterministic reproduction of the original fault (documented seed / injection points).
- ThreadSanitizer (or equivalent) clean run after the fixes.
- Unit tests for `compute_setpoint` at extreme values: `pedal_pct = 100`, `ax_mg` fully negative,
  `wheel_speed = 65535`, all-zero frame, stale frame.
- A soak test running the simulated system for a large number of cycles with randomized timing,
  asserting the setpoint never leaves `[0, 10000]` and never deviates from the value implied by a
  consistent input frame.
