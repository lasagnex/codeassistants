### T011 – Brake Pad Measurement Intake Pipeline (Hard)

**Difficulty:** Hard
**Category:** Data pipeline / ETL automation, multi-format integration, idempotency & recovery

## Task Description
Every workshop of the fleet drops its brake pad measurements into a shared folder. The exports come
from three generations of diagnostic tester plus one workshop that maintains its own spreadsheet, so
the same information arrives in four different shapes, with different units, different date formats
and occasional garbage.

Build the automation that turns this folder into a trustworthy data warehouse and a service report,
and that can be re-run every night without human supervision.

> **Starting material:** `base/inbox/` (8 export files) and `base/master/vehicles.csv`.

The inbox is a **read-only** share: the pipeline must never move, rename or delete anything in it.
What has already been ingested is tracked by the pipeline itself, not by the file system.

### Source formats

| Source system | File pattern | Format |
|---------------|--------------|--------|
| Tester A | `tester_a_<date>.json` | JSON, `records[]` |
| Tester B | `tester_b_export_<date>.xml` | XML, `vehicle` → `measurement` elements, `unit` attribute is `mm` **or** `in` |
| Legacy tester | `legacy_pad_*.txt` | fixed width, see below |
| Workshop | `workshop_*.csv` | `;`-separated, decimal comma, `unit` column, free-text VIN column |

**Tester A changed its export schema** with a firmware update. Older files carry
`pad_thickness_mm` and `side: "left"/"right"`; newer ones carry `pad_remaining_pct` (percent of an
unworn pad) and `side: "L"/"R"`. No file states its schema version — infer it from the payload, and
keep the two readers separable so a third variant can be added without touching the core.

**Legacy fixed-width layout** (1-based columns), between an `HDR` and a `TRL` record; the `TRL`
record carries the record count and must be validated:

| Columns | Field |
|---------|-------|
| 1–17 | VIN |
| 19 | axle number |
| 21 | side, `L` or `R` |
| 23–28 | pad thickness in 1/100 mm, zero padded |
| 30–37 | measurement date, `YYYYMMDD` |

### Master data
`master/vehicles.csv` (`vin,model,axle_count,pad_new_mm,fleet`) is authoritative: it defines which
vehicles exist, how many axles each has, and how thick an unworn pad is on that vehicle. The
percent readings of the newer Tester A schema can only be converted using it.

## Requirements

### Normalisation
- Canonical record: `vin, axle, side, measured_at_utc, thickness_mm, source_file, source_system`.
- VINs are normalised to upper case with surrounding noise stripped (whitespace, a `VIN:` prefix).
- Timestamps are normalised to UTC. Values arrive naive, with `Z`, and with an explicit offset; a
  date without a time is interpreted as 00:00 `Europe/Berlin`.
- Inch readings are converted (`1 in = 25.4 mm`); results are stored in mm.

### Validation — rejected per record, with a reason
`unknown_vin`, `invalid_axle` (higher than the vehicle's axle count), `implausible_thickness`
(negative, or greater than the vehicle's `pad_new_mm`), `malformed` (missing field, non-numeric
value). A file that cannot be parsed at all is **quarantined as a whole**, with the error recorded;
one broken file must not stop the run.

### Deduplication and conflict resolution
Two records describe the same measurement when `vin`, `axle` and `side` match and the timestamps lie
within 24 h of each other. Resolution:
- agreement within **0.3 mm** → keep the record from the higher-precedence source,
  `tester_b > tester_a > legacy > workshop`;
- difference above 0.3 mm → **neither** value is trusted: both go to the conflicts table, the pad is
  excluded from the report for that date, and the run is flagged for human review.

### Idempotency and recovery
- Ingestion is keyed on **file content** (SHA-256), not on the file name: the same export re-dropped
  under a different name is recognised and skipped.
- A second run over an unchanged inbox ingests nothing, changes no output row and reports zero new
  files.
- The run is crash safe: killing the process mid-run must leave the warehouse consistent and a
  re-run must complete the work. State how this is achieved (staging + atomic commit, transactions).
- Concurrent runs are prevented by a lock; the second run exits with code `3` instead of corrupting
  anything.

### Output contract — exact names, so runs can be compared
- `out/warehouse.sqlite` with the tables
  `measurements(vin, axle, side, measured_at_utc, thickness_mm, source_file, source_system)`,
  `rejects(source_file, record_ref, reason, raw)`,
  `conflicts(vin, axle, side, measured_at_utc, source_a, thickness_a, source_b, thickness_b)`,
  `files(path, sha256, source_system, status, records_ok, records_rejected, processed_at, error)`.
- `out/manifest_<run_id>.json` with `run_id, started_at, finished_at, files_new, files_skipped,
  files_quarantined, records_ingested, records_rejected, conflicts_unresolved, exit_code`.
- `out/report_fleet.csv` with the columns
  `vin,fleet,axle,side,latest_thickness_mm,measured_at,status,wear_rate_mm_per_day,projected_replace_date`,
  one row per pad, worst first. Status by remaining thickness: `>= 8.0` `OK`,
  `>= 4.0 and < 8.0` `WARN`, `< 4.0` `REPLACE`. The wear rate is a least-squares fit over all
  accepted measurements of that pad and the projection is the date it reaches 4.0 mm; both are empty
  when there are fewer than two measurements or the fit does not show wear.

### Operation
- One documented command runs the pipeline; input, master and output paths are arguments, nothing
  is hardcoded to the provided pack. `--dry-run` reports what would be ingested without writing.
- Exit codes: `0` clean, `1` rejects or unresolved conflicts present, `2` fatal error, `3` lock held.
- Structured log to stderr; a scheduled invocation (cron entry, systemd timer or CI workflow) is
  included and documented.

## Expected Deliverables
- The pipeline source, runnable on a fresh clone with one documented command.
- The outputs produced from the provided pack: `warehouse.sqlite`, the manifest and
  `report_fleet.csv`, plus the exit code returned.
- A README covering the architecture, how a new source format is added, the conflict policy, the
  crash-safety mechanism, and every assumption made about the data.
- A short data-quality note listing every defect found in the pack and how it was handled.

## Testing
- Unit tests per reader: both Tester A schema variants, the inch conversion, the `TRL` validation,
  the timestamp normalisation (naive, `Z`, offset, date-only) and the VIN cleanup.
- Tests for each reject reason and for the quarantine of the unparseable file.
- Conflict tests covering both sides of the 0.3 mm threshold and the source precedence order.
- An idempotency test: run twice, assert the second run ingests nothing and the outputs are
  byte-identical; plus a test that the duplicate export under a different name is skipped.
- A recovery test: interrupt the run and assert the re-run produces the same warehouse as an
  uninterrupted one.
- An end-to-end test on the provided pack asserting the row counts of all four tables and the
  status of at least the pads in `REPLACE`.
