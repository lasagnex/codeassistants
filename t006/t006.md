### T006 – Framework Migration: Diagnostic Dashboard (Medium)

**Difficulty:** Medium
**Category:** Framework migration, full stack, API design

## Task Description
An internal EBS (Electronic Braking System) diagnostic dashboard exists as a single-file Flask
application with server-rendered Jinja templates and jQuery polling. It shows live ECU signals and
the active Diagnostic Trouble Codes of connected vehicles.

Migrate it to a **FastAPI backend + a modern frontend framework** (React, Vue or Svelte — your
choice, state it in the README), keeping every existing feature working.

> **Starting code:** `base/` contains the legacy application

### Legacy app
- Flask, one `app.py`, in-memory data, Jinja templates, jQuery polling every 2 s.
- Routes:
  - `GET /` – vehicle list (VIN, model, online flag, number of active DTCs)
  - `GET /vehicle/<vin>` – detail page: live signals (front/rear brake pressure, reservoir
    pressure, pad wear per axle, ambient temperature) and a DTC table
    (code, description, status active/stored, occurrence count, first/last seen)
  - `POST /vehicle/<vin>/clear_dtc` – clears stored DTCs, redirects back
  - `GET /api/vehicle/<vin>/signals` – JSON used by the polling code
- Signals are produced by a simulator that mutates the in-memory state every second.
- 4 vehicles, 7 DTC types (e.g. `B1204 Wheel speed sensor FL – no signal`).
- `clear_dtc` removes **stored** DTCs only — active faults remain. Unknown VIN gives `404` on
  both the HTML and the JSON route. Both behaviours are part of feature parity.

## Requirements
- **Backend (FastAPI)**
  - Typed request/response models (Pydantic) for every endpoint; automatic OpenAPI docs available.
  - Replace 2-second polling with a WebSocket (or SSE) push of live signal updates.
  - Proper REST semantics: `DELETE /api/vehicles/{vin}/dtcs` instead of the `POST ... /clear_dtc`
    redirect; correct status codes; `404` for an unknown VIN with a structured error body.
  - Separate the simulator from the web layer so it can be replaced by a real CAN source later.
  - CORS configured for the frontend dev server.
- **Frontend**
  - Vehicle list and vehicle detail views with client-side routing.
  - Live-updating signal display driven by the WebSocket/SSE stream, with a visible
    connection status and automatic reconnect on drop.
  - DTC table with sorting and a filter for active/stored, plus a clear-DTC action with confirmation.
  - Warning styling when a signal leaves its plausible range (e.g. reservoir pressure < 6.5 bar).
  - Works on a narrow window; no build-time errors, no console errors.
- The whole stack must come up locally from a single documented entry point.

## Expected Deliverables
- The migrated stack: FastAPI backend and the new frontend application.
- A `docker compose up` setup or two documented commands that bring the whole stack up locally.
- The backend, frontend and end-to-end test suites.
- Screenshots or a video of the working app.
- A README with the before/after architecture, the chosen frontend framework and why, and
  migration notes listing what changed for API consumers.

## Testing
- Backend: tests for every endpoint (happy path, unknown VIN, clearing DTCs twice), plus a test
  that connects to the WebSocket/SSE endpoint and asserts that updates arrive.
- Frontend: component tests for the DTC table (sorting, filtering) and the signal warning logic.
- End-to-end: automated browser test covering "open list → open vehicle → see values update →
  clear DTCs → table updates".
